[P style=Title] Ecommerce Platform Development Blueprint
[P style=Subtitle] React and Node.js store with a complete administration panel
[P style=Small] Prepared 30 October 2026  |  Product specification and engineering guide
[P style=] Build a single store where you upload products and categories, sell to registered customers or guests, accept approved payment methods, track shipments, and manage the full order lifecycle. The design follows the search-first structure and deal cards in your eBay screenshots, with your own brand and visual identity.
[P style=Heading2] Recommended implementation
[P style=] Use Next.js for the React storefront and admin interface, Tailwind CSS with shadcn/ui, a NestJS Node.js API, PostgreSQL, and background workers. Render product content on the server so visitors and search engines receive useful HTML. Keep inventory, orders and payments authoritative in PostgreSQL.
[TABLE]
| Decision | Recommended scope |
| Business model | One merchant, fixed-price products, physical goods, category hierarchy and variants. |
| Customer access | Accounts with sign in and sign out, plus guest checkout without registration. |
| Payments | Provider adapters; confirm merchant eligibility before integration. Payoneer Checkout is conditional. |
| Growth | Automatic SEO foundations, useful product content, measured acquisition and consent-based email. |
| Later extensions | Multi-seller onboarding, auctions, seller payouts and complex marketplace disputes require a separate release. |
[/TABLE]
[P style=Small] 
[P style=] No strategy can guarantee rankings or 100% customer conversion. The goal is a reliable store and a measurable process that improves qualified traffic, purchase rate and repeat orders.

[P style=Heading1] 2 Visual direction from your references
[P style=] Use the browsing logic visible in the supplied screens: a prominent search bar, category navigation, a wide promotion area, and product cards with clear prices. Use original photography, copy, logo and colors for your own store.
[P style=CaptionText] Reference 1  Search and category navigation above a wide promotional hero
[P style=CaptionText] Reference 2  Deal cards with consistent image areas and readable pricing
[P style=Heading2] Translate the references into your store
[P style=] Place search ahead of decoration. Give each product an uncluttered image area, a two-line name, current price, genuine discount information, delivery estimate and wishlist action. Use one primary action per context. Promotional banners should link to real collections with valid stock and dates.
[P style=] For a first visit, promote categories and deals. Show account benefits as a secondary invitation while keeping shopping and guest checkout available.

[P style=Heading2] Design system
[P style=] Start with white surfaces, dark text, a single blue or green primary color, neutral borders, and restrained shadows. Suggested tokens: page background #FFFFFF; text #111827; primary #2563EB; muted #F3F4F6; border #D1D5DB. Use an 8 px spacing scale, 12 to 16 px card radii, and a consistent square product image ratio. Final colors must pass contrast checks.

[P style=Heading2] Components and accessibility
[P style=] Use shadcn/ui navigation, sheet, dialog, tabs, select, form, skeleton, pagination and toast components. Build admin tables with TanStack Table. Choose one component primitive family and use it consistently. [8, 19, 20]
[P style=] Include visible keyboard focus, semantic headings, labeled inputs, descriptive errors, meaningful image alt text and reduced motion. Aim for WCAG 2.2 AA. Prefer a static hero; if a carousel is added, provide pause and keyboard controls. Test checkout with keyboard and screen readers.

[P style=Small] 
[P style=Heading2] Staff permissions
[P style=] Owner manages roles and integrations. Catalog staff edit products and stock. Fulfillment staff access orders and shipments. Support staff see only necessary customer details. Finance staff reconcile and refund. Marketing staff manage content and consented audiences. Check each permission on the server; hiding a button is only a UI convenience.
[P style=Heading2] Example completion workflow
[P style=] A catalog editor creates a product, adds images and variants, enters opening stock, validates the preview and publishes. Fulfillment staff receive a paid order, generate a packing list, create a shipment and record tracking. Finance can issue a partial refund with a reason. Every change records the actor and timestamp.

[P style=Heading1] 5 Application architecture and library choices
[P style=] Start with a modular monolith: one API codebase with clear domain modules, plus a separate worker process. It is easier to operate than early microservices and preserves transaction boundaries for stock and orders.
[TABLE]
| Layer | Choice and responsibility |
| React application | Next.js App Router and TypeScript. Public catalog uses server rendering and explicit caching. Admin and account data are private and uncached. |
| UI and forms | Tailwind CSS, shadcn/ui, Lucide icons, React Hook Form and Zod for client validation. Mirror critical rules in server DTOs. |
| State and reports | TanStack Query for interactive server state; TanStack Table for admin grids; Recharts for simple charts. Keep cart totals server-authoritative. |
| Node.js backend | NestJS with Express adapter, validation pipes, permission guards, domain services and OpenAPI documentation. |
| Database | PostgreSQL with versioned migrations. Prisma is a suitable typed ORM; use parameterized SQL for locks and specialized indexes. |
| Background work | Redis and BullMQ for jobs; PostgreSQL transactional outbox for durable publication, email and reconciliation events. |
| Files and search | S3-compatible object storage and CDN. Begin with PostgreSQL full-text search; add Meilisearch or OpenSearch after measured need. |
| Quality and telemetry | Vitest or Jest, Playwright, structured logs, OpenTelemetry and an error tracker. Pin compatible supported package versions. |
[/TABLE]
[P style=Small] 
[P style=Heading2] Request and event boundaries
[P style=] Browser requests go to the Next.js application and a same-origin /api/v1 reverse proxy to NestJS. NestJS reads and writes PostgreSQL. It calls payment and courier adapters only from the server. Workers consume durable outbox events and send email, refresh search documents, invalidate catalog caches and update product feeds.
[P style=] The browser receives publishable provider configuration only. Database credentials, payment secrets, webhook secrets and signing keys stay in server secret storage. Separate development, staging and production databases, buckets and provider credentials.
[P style=Heading2] Why Next.js is included
[P style=] Next.js remains a React application and supports your requested stack. Its server rendering and metadata APIs give product pages and category pages a stronger technical foundation than relying only on a browser-rendered SPA. NestJS owns commerce rules; Next.js owns page composition. [4, 5, 17, 18]
[P style=] 

[P style=Heading1] 6 Database schema for identity and catalog
[P style=] Use UUID primary keys, UTC timestamptz timestamps and explicit foreign keys. In the tables below, PK means primary key, FK means foreign key, UQ means unique, and ? means nullable. Field lists are the implementation dictionary, including the supporting entities required beyond the starter SQL.
[TABLE]
| Table | Main fields | Rules |
| users | id PK, email_normalized UQ, password_hash?, name, phone?, status, email_verified_at?, created_at | Never store plaintext passwords. Social-only accounts may omit password_hash. |
| sessions and tokens | sessions: id, user_id FK, token_hash UQ, expires_at, revoked_at?; auth_tokens: user_id, kind, token_hash, expires_at, used_at? | Rotate session IDs on login; consume reset and verification tokens once. |
| roles and permissions | roles, permissions, user_roles, role_permissions; each join uses a composite PK | Permission keys such as products.publish and orders.refund. |
| addresses | id, user_id FK, recipient, phone, country, region, city, postal_code?, address lines | Address book is editable; order addresses are independent snapshots. |
| categories | id PK, parent_id? FK to categories, slug UQ, name, description, sort_order, active | Prevent cycles in service; publish only useful category landing pages. |
| products | id, slug UQ, title, brand?, description, status, primary_category_id FK, published_at?, version | Status: draft, scheduled, published, archived. Explicit publish validation. |
| product_variants | id, product_id FK, sku UQ, gtin?, option_values jsonb, price_minor, compare_at_minor?, currency, active | Each sellable item has a variant, including products with no visible options. |
| media and attributes | product_media: product_id, variant_id?, object_key, alt_text, sort_order; attributes, category_attributes, product_attribute_values | Validate file type and dimensions. Typed attributes power reliable filters. |
[/TABLE]
[P style=Small] 
[P style=Heading2] Catalog relations
[P style=] A category has many products and may have child categories. A product has many variants and media assets. Add product_categories(product_id, category_id) with a composite PK when a product belongs to several collections; retain one primary category for breadcrumbs. A variant has stock records per warehouse.
[P style=] Use product_seo(product_id PK/FK, meta_title?, meta_description?, canonical_override?, index_policy, content_version). Keep generated defaults separate from staff overrides so later imports do not erase editorial work.
[P style=] 

[P style=Heading1] 7 Database schema for checkout and money
[TABLE]
| Table | Main fields | Integrity requirement |
| inventory_stock | variant_id FK, warehouse_id FK, on_hand, reserved; composite PK | CHECK on_hand >= 0, reserved >= 0 and reserved <= on_hand. |
| stock_reservations | id, order_id FK, variant_id FK, warehouse_id FK, quantity, expires_at, state | UQ order/variant/warehouse. States active, committed, released. Changes are atomic. |
| inventory_movements | id, variant_id, warehouse_id, delta_on_hand, delta_reserved, reason, reference, actor_id?, created_at | Append-only history. Prevent duplicate movements for the same event and action. |
| carts and cart_items | cart: id, user_id?, guest_token_hash?, expires_at; item: cart_id, variant_id, quantity | UQ cart/variant; quantity > 0. Merge on login without exceeding stock. |
| orders | id, order_number UQ, user_id?, email, phone, order_status, payment_status, fulfillment_status, currency, totals_minor, address snapshots | Guest orders have user_id NULL. Freeze prices, addresses, tax and delivery at placement. |
| order_items | id, order_id FK, variant_id?, sku_snapshot, title_snapshot, options_snapshot, quantity, unit_price_minor, discount_minor, tax_minor | Product edits or archive must never change historical order amounts. |
| payments | id, order_id FK, provider, provider_reference UQ per provider, amount_minor, currency, state, idempotency_key | One order can have multiple attempts; only verified payment results change paid status. |
| refunds and returns | refunds: payment_id, amount_minor, reason, state, provider_ref; returns: order_id, state; return_items: order_item_id, quantity, disposition | Lock against over-refunds; count completed and pending refunds. Restock after inspection. |
| shipping | shipments: order_id, carrier, tracking_number, state; shipment_items: shipment_id, order_item_id, quantity; tracking_events: shipment_id, event_key, occurred_at, status | Multiple shipments per order. UQ carrier event identity; enforce remaining quantities. |
[/TABLE]
[P style=Small] 
[P style=Heading2] Money model and reconciliation
[P style=] Store amounts as BIGINT minor units plus ISO currency, and serialize large amounts as decimal strings in JSON. Use currency exponent metadata; never assume every currency uses two decimals. Avoid JavaScript floating-point arithmetic for money. Keep authorized, captured, refunded and settled amounts distinct.
[P style=] Order total equals line subtotals minus allocated discounts plus tax and shipping. Store provider fees, net settlement, currency conversion and settlement batches separately. Gross sales and available cash are different reports. Do not combine unlike currencies into one unconverted total.
[P style=]

[/TABLE]
[P style=Small] 
[P style=Heading2] Indexes and deletion policies
[P style=] Index every high-volume FK and common query: orders(user_id, created_at), orders(email_normalized, created_at), products(status, published_at), variants(product_id), payments(order_id), and tracking_events(shipment_id, occurred_at). Use GIN for full-text search and measured JSONB filters; avoid indexing every attribute blindly.
[P style=] Use a unique index on lower(email) or normalize before writing. Archive products rather than cascading deletion into orders. Redact or anonymize customer data through a controlled retention process while preserving legally required order records. Audit access and test backup restoration.
[P style=]

[P style=Heading1] 11 Customer API and controller contracts
[P style=] Use /api/v1 as the public API prefix and OpenAPI as the contract. Controllers accept DTOs, authenticate callers and delegate to services. Services own stock, pricing and state transitions; repositories own database access. Return only allowlisted response fields.
[TABLE]
| Controller | Routes | Access and behavior |
| AuthController | POST /auth/register, /login, /logout, /forgot-password, /reset-password; POST /auth/verify-email | Public or session as appropriate; rate limits; generic recovery responses; CSRF on browser mutations. |
| AccountController | GET/PATCH /me; CRUD /me/addresses; GET /me/orders; GET /me/sessions; DELETE /me/sessions/:id | Authenticated owner only. Reauthenticate sensitive changes and revoke sessions when required. |
| CatalogController | GET /categories; GET /products; GET /products/:slug; GET /search | Public published products only; validated filters, bounded page size and deterministic sort. |
| CartController | POST /carts; GET /cart; POST/PATCH/DELETE /cart/items/:variantId | Session-bound account cart or high-entropy guest cart cookie; no client price acceptance. |
| CheckoutController | POST /checkout/quote; POST /orders; POST /orders/:id/payment-session | Guest or account; cart capability or ownership; idempotency on placement and payment creation. |
| OrderController | GET /orders/:id; POST /orders/:id/cancel; POST /orders/:id/returns | Authenticated owner or narrowly scoped guest capability; state-based cancellation rules. |
| GuestAccess | POST /guest/orders/request-access; POST /guest/orders/verify-access; GET /guest/orders/:id | Generic request response, short-lived code or link, rate limit and order-scoped session. |
| Wishlist and Review | GET/POST/DELETE /me/wishlist; POST /products/:id/reviews | Account owner; validate purchased item before verified-purchase label; moderation before display. |
| ConsentController | GET/POST /consent; POST /newsletter/subscribe; POST /email/unsubscribe | Separate purpose flags; verification and abuse limits; unsubscribe works without account login. |
[/TABLE]
[P style=Small] 
[P style=Heading2] Response conventions
[P style=] Use a request ID in every response. Validation errors identify fields without leaking internals. Typical outcomes: 201 created; 400 invalid input; 401 no valid session; 403 forbidden; 404 unavailable resource; 409 stock, version or idempotency conflict; 422 unsupported business action; 429 throttled. Use a consistent JSON shape: code, message, fieldErrors and requestId.
[P style=] Never let a URL order ID alone grant access. Staff access, customer ownership and guest capabilities are independent authorization paths. Enforce query limits server-side and paginate expensive lists.
[P style=]

[P style=Small] 
[P style=Heading2] Controller settings
[P style=] Register a global validation pipe, session guard and permission guard. Mark public endpoints explicitly. Add audit interceptors to sensitive admin operations, an exception filter for safe error responses, and request-size limits before parsing. Webhooks bypass browser CSRF only because they use provider authentication; they do not bypass signature verification. [17, 18]
[P style=Heading2] Service separation
[P style=] ProductService owns catalog writes; InventoryService owns movements and reservations; CheckoutService freezes totals; PaymentService coordinates adapters and reconciliation; OrderService enforces order actions; ShipmentService maps courier states. Controllers must not contain ad hoc SQL or duplicate payment logic.

[P style=Heading1] 13 Project layout and initial configuration
[P style=] Use a TypeScript monorepo with one package manager and a lockfile. Select a supported Node.js LTS at kickoff, pin compatible package versions, and document upgrade ownership. Keep API and UI contracts shared without importing server secrets into the frontend.

[P style=Code]   app/(store)/             Home, category, product, checkout
[P style=Code]   app/(account)/           Profile, orders and addresses

[P style=Heading1] 14 Accounts sessions and guest access
[P style=Heading2] Account lifecycle
[P style=] Registration normalizes email, hashes the password with Argon2id, stores an unverified account and sends a single-use verification link. Login checks credentials, throttles attempts, rotates the session token and records a server-side session. Logout revokes that session and clears the cookie. Password reset expires existing sessions according to the recovery policy. [9]
[P style=] Use a mature authentication library or carefully reviewed module. Allow password managers, long passphrases and breached-password checks. Provide generic login and recovery responses where appropriate to reduce account enumeration. Admin staff must enroll MFA, with audited recovery.
[P style=Heading2] Session design
[TABLE]
| Setting | Specification |
| Cookie | __Host-session with Secure, HttpOnly, Path=/, no Domain and SameSite=Lax for the same-origin architecture. |
| Storage | High-entropy random session token in cookie; store its hash server-side. Keep roles and revocation authority on the server. |
| Expiry | Starting policy: customers 7 days idle and 30 days absolute; staff 30 minutes idle and 12 hours absolute. Tune after risk review. |
| CSRF | Validate CSRF token and allowed Origin on browser state changes. SameSite alone is not the entire CSRF defense. |
| Sensitive actions | Reauthenticate for email change, MFA reset, role changes, gateway configuration and refunds. Notify the account owner. |
| Browser storage | Do not put bearer authentication tokens in localStorage. Cart UI state can be local; authoritative cart access is protected. |
[/TABLE]
[P style=Small] 
[P style=Heading2] Guest orders without an account
[P style=] Checkout collects the delivery and contact details needed to fulfill the order and leaves orders.user_id empty. Do not create a password or subscribe the buyer silently. Email the receipt and a secure access path. Allow a later account invitation without blocking the purchase.
[P style=] Guest tracking begins with order number and email, returns a generic result, then sends a one-time link or code. Store only a token hash, expire it quickly, and exchange it for a restricted order session. Redact addresses on tracking views and set Referrer-Policy: no-referrer on token exchange pages.
[P style=] Claiming a guest order requires verification of the same email address. A matching typed email is insufficient. After verification, link only the relevant orders and record the action. Protect lookup, verification and resend endpoints with rate and abuse limits.

[P style=Heading1] 15 Security requirements and abuse controls
[TABLE]
| Risk area | Implementation requirement | Acceptance evidence |
| Unauthorized access | Deny by default; server-side permission and object ownership checks on every protected route. | A second customer cannot read or modify another customer order. |
| Input and injection | DTO allowlists, parameterized queries, rich-text sanitization, URL validation and bounded filters. | Invalid fields rejected; stored script content cannot execute. |
| Payment tampering | Calculate totals server-side; verify signed callbacks and provider status; compare order, amount and currency. | Browser return URL cannot mark an unpaid order paid. |
| Race conditions | Row locks or conditional stock updates, database transactions, uniqueness and idempotent side effects. | Concurrent attempts to buy the last unit produce one successful allocation. |
| Web security | HTTPS, HSTS after validation, strict CSP, clickjacking protection, safe redirects and least-privilege CORS. | Approved payment SDK works; unapproved script origin is blocked. |
| File upload | Presigned upload, size/type limits, magic-byte check, image re-encoding, malware checks and private staging. | An executable or oversized file cannot become a public product image. |
| Secrets and logs | Secret manager, rotation, encryption at rest, log redaction and separate production credentials. | No password, full card, token or sensitive address appears in logs. |
| Fraud and automation | Rate limits, suspicious login alerts, checkout velocity checks and risk-based challenges. | Retry abuse is throttled without blocking normal guest purchase. |
| Supply chain | Dependency lockfile, security review, vulnerability scan and minimal runtime permissions. | Build uses reviewed artifacts and no known critical exploitable dependency. |
| Operational access | Private database network, least-privilege service users, admin MFA and immutable audit export. | Restoration succeeds; privilege change and refund have traceable actors. |
[/TABLE]

[P style=Heading2] Payment data boundary
[P style=] Use hosted checkout or provider-hosted fields. Keep PAN and CVV outside your application, logs and database; store only provider references and permitted masked metadata. This reduces card-data exposure but does not automatically remove all PCI obligations. Confirm the applicable validation scope with the payment provider.
[P style=Heading2] Controls must be tested
[P style=] Include IDOR tests, account recovery tests, expired session tests, CSRF rejection, webhook replay, duplicate refunds, malicious upload, unauthorized export and concurrent stock tests. Security acceptance belongs in each phase, with a focused review before accepting live payments. [9, 10]

[P style=Heading1] 16 Checkout pricing and stock integrity
[P style=] Guest and registered buyers use the same pricing and inventory services. Treat the cart as a request to purchase; it does not reserve stock indefinitely. Present a final quote with an expiry and recalculate it when placing the order.
[P style=Heading2] Order placement algorithm
[P style=ListNumber] Accept variant IDs, quantities, address, shipping choice and coupon. Resolve the cart from its session or guest capability. Ignore client prices and totals.
[P style=ListNumber] Require an idempotency key scoped to the actor and operation. Persist a request hash; the same key and payload returns the same order, while a changed payload returns conflict.
[P style=ListNumber] In a database transaction, lock stock rows in deterministic order, validate available stock and allocate discounts, tax and shipping from current server rules.
[P style=ListNumber] Create the pending order and immutable line and address snapshots. Reserve stock for a defined payment window, for example 15 minutes where the provider supports it. Add outbox events and commit.
[P style=ListNumber] Outside the database transaction, create the provider checkout session with a stable payment attempt ID and provider idempotency where available. Persist the reference. Never hold stock-row locks while making a network call.
[P style=ListNumber] On a verified successful capture, lock the order, payment and reservations. Check reference, amount and currency. Commit stock once, update payment state and enqueue the confirmation through the outbox.
[P style=Heading2] State and failure rules
[TABLE]
| Situation | Required result |
| Two buyers want the final unit | Only one reservation succeeds; the other receives a clear stock conflict and a refreshed cart. |
| Payment fails or session expires | Cancel or expire the attempt, release its active reservation once and allow a controlled retry. |
| Provider request times out | Query or reconcile the existing attempt before creating another charge; show processing rather than false failure. |
| Payment arrives after stock release | Attempt atomic reallocation; if unavailable, place on exception hold and refund according to policy. Do not silently oversell. |
| COD order | Record payment_due and payment method COD. Allocate stock after confirmation; record collection and courier remittance separately. |
| Discount or tax changes | Freeze accepted totals on the placed order. Requote before placement if the original quote is no longer valid. |
[/TABLE]
[P style=Small] 
[P style=] Do not report a payment authorization as captured revenue. Support authorized, captured, failed, cancelled, partially refunded and refunded payment states independently from shipping. [10]

[P style=Heading1] 18 Order tracking shipping and returns
[P style=Heading2] Separate order payment and fulfillment states
[P style=] Order states: pending, confirmed, on_hold, cancelled and completed. Payment states: unpaid, processing, authorized, captured, partially_refunded, refunded and failed. Fulfillment states: unfulfilled, partially_shipped, shipped, delivered and returned. Derive customer labels from these axes rather than one overloaded status field.
[TABLE]
| Step | System action | Customer view |
| Placed | Freeze order details, record payment state and send the correct receipt or pending-payment notice. | Order received with item list and payment result. |
| Confirmed | Payment verified or COD confirmation accepted; warehouse allocation and fraud hold reviewed. | Confirmed and preparing your order. |
| Packed and shipped | Create carrier shipment, label and tracking reference; assign shipped quantities to order items. | Carrier, tracking link and shipped items. |
| In transit | Authenticate carrier webhook or poll the carrier API; normalize events and preserve raw status mapping. | Timeline with last update time and delivery estimate. |
| Delivered or exception | Record delivered, delayed, failed delivery or returned-to-origin. Alert staff about unresolved exceptions. | Delivered status or clear next step and support action. |
| Return and refund | Approve eligible items, receive goods, inspect, choose restock disposition and process refund. | Return progress and refund amount with expected processing information. |
[/TABLE]

[P style=Heading2] Carrier integration
[P style=] Choose a courier after checking coverage, COD remittance, tracking API access, labels, pickup workflow, claims and return-to-origin costs. Implement a carrier adapter with createShipment, cancelShipment and fetchTracking. Start with one carrier and allow a staff-entered tracking fallback with audit history.
[P style=] Deduplicate carrier events, store their occurrence time and prevent a delayed in-transit message from overwriting delivered status. Support multiple packages, partial shipment and separate tracking numbers. Show the most recent successful synchronization; do not display â€œliveâ€ when the courier has not provided a new event.
[P style=Heading2] Secure tracking and notification rules
[P style=] Registered buyers open their own orders. Guests verify access through the email flow on page 14. Public carrier tracking links may show logistics progress; your store must not reveal recipient addresses from an order number alone. Notify only meaningful changes, deduplicate messages and route delivery exceptions to a staff queue.

[P style=Heading1] 19 Automatic publishing and SEO updates
[P style=] Uploading a file creates a draft asset; publishing a validated product creates the public page. Provide an optional auto-publish mode only for trusted imports that pass the same checks. The admin should show each step and any failed jobs.
[P style=Heading2] Publishing workflow
[P style=ListNumber] Validate title, primary category, SKU uniqueness, variant price and currency, images, alt text, shipping data and inventory policy. Reject incomplete or unsafe content.
[P style=ListNumber] Build a stable slug, default SEO title and description from verified attributes. Preserve staff overrides. Generate useful copy from factual product data; AI suggestions require a factual review.
[P style=ListNumber] Commit the catalog changes and product.published or product.updated event in one PostgreSQL transaction. Increment the product version.
[P style=ListNumber] Workers refresh catalog search, invalidate product and category caches, regenerate relevant sitemap entries, and schedule Merchant Center feed updates where the store is eligible.
[P style=ListNumber] Verify the rendered product HTML, metadata, canonical URL, image URLs and Product offer data. Publish the event version to prevent old retries overwriting newer content.

[P style=Heading1] 21 Customer acquisition and conversion strategy
[P style=] There is no method that produces customers with 100% certainty. Use small experiments with margin-based spending limits, then scale the combinations of products, audiences and offers that produce profitable orders.
[P style=Heading2] The first ninety days after launch
[TABLE]
| Period | Action | Decision measure |
| Days 1 to 14 | Launch 20 to 50 well-documented products in one category. Check mobile checkout, delivery coverage, support and real product photography. | Find usability failures; measure checkout completion and payment success. |
| Days 15 to 30 | Publish useful category guides and comparisons; test one acquisition channel and two offers. Use authentic product demonstrations. | Qualified visits, add-to-cart rate, paid orders and contribution margin by channel. |
| Days 31 to 60 | Improve high-impression low-click pages, simplify checkout and expand proven categories. Collect genuine reviews after delivery. | Organic click-through, conversion, returns and cost per new customer. |
| Days 61 to 90 | Scale profitable campaigns, negotiate fulfillment costs, improve product bundles and introduce a relevant replenishment or loyalty offer. | Repeat purchase, cohort margin, refund rate and inventory turnover. |
[/TABLE]
[P style=Small] 
[P style=Heading2] Store changes that support sales
[P style=ListBullet] Show the full payable total and delivery estimate before payment. State returns and warranty clearly. Let buyers check out as guests.
[P style=ListBullet] Keep photos and descriptions accurate. Show true availability, useful variants and relevant product comparisons. Avoid fake countdowns or unsupported discount claims.
[P style=ListBullet] Make local shipping coverage, support hours and contact methods visible. Use bundles and free-shipping thresholds only when the margin supports them.
[P style=ListBullet] Use consented email offers, back-in-stock requests, review requests and repeat-customer rewards. Match each offer to stock and customer interest.
[P style=Heading2] Metrics and spending limits
[P style=] Conversion rate = completed paid orders divided by eligible sessions; report confirmed COD orders separately. CAC = acquisition spend divided by new customers acquired. Contribution per order = net revenue less product cost, payment fees, delivery subsidy, expected returns and variable fulfillment cost.
[P style=] Example only: if a PKR 5,000 order leaves PKR 1,000 before advertising, PKR 1,000 is an upper break-even acquisition cost before fixed costs. A lower target leaves room for profit. Do not justify high spending with assumed lifetime value before repeat-purchase evidence exists. Compare experiments over sufficient samples; record attribution uncertainty.

[P style=Heading1] 22 Cookies customer identity and privacy
[P style=] Cookies can recognize a browser and remember permitted activity; they cannot reveal an anonymous visitorâ€™s email address. Collect email directly through checkout, account creation or a voluntary subscription. Explain each purpose and use a consent-first marketing design for international reach.
[TABLE]
| Purpose | Data and behavior | Customer control |
| Essential shopping | Session, cart, checkout security and fraud controls needed to provide the requested service. | Explain in the cookie notice; keep shopping available without optional tracking. |
| Analytics | Pseudonymous page, product, cart and conversion events after the selected consent policy allows them. | Off by default in this recommended baseline; accept or reject with comparable prominence. |
| Advertising | Ad pixels, audience exports and behavioral targeting only after the appropriate permission. | Separate optional choice; honor withdrawal and applicable opt-out signals. |
| Email marketing | Address supplied by the person plus a separate unchecked marketing choice. | Record source, purpose, notice version and time; easy unsubscribe in every promotional email. |
| Service messages | Receipts, password recovery, shipment and return notices for the requested transaction. | Keep the content operational; do not add promotional blocks to bypass marketing preferences. |
[/TABLE]

[P style=Heading2] Identification flow
[P style=] A new visitor may receive a random analytics ID only when permitted. If the visitor later signs in or submits their email, associate only the activity allowed by the disclosed purposes and current permissions. Do not attach past rejected tracking, infer identity from IP addresses, buy anonymous-email matches or use fingerprinting to evade refusal.
[P style=Heading2] Implementation checklist
[P style=ListBullet] Build a preference panel with essential, analytics and advertising purposes. Store the current choice and append grant or withdrawal events. Block optional tags before consent.
[P style=ListBullet] Validate consent server-side before marketing jobs, not just in the browser. An analytics choice is not an email subscription. A purchase email is not automatic permission for deals.
[P style=ListBullet] Offer access, correction and deletion requests. Set retention periods, for example 90 days for raw behavioral events as a starting product policy, and document separate order-record retention requirements.
[P style=ListBullet] Keep emails and addresses out of analytics payloads and URLs. Restrict staff exports, redact logs and review third-party processor settings.
[P style=] UK ICO guidance distinguishes essential cookies from optional tracking and sets specific electronic-marketing requirements. This blueprint chooses a stricter consent-first default; applicable obligations still depend on customer location and the way the store operates. Review target markets before launch. [15, 16]

[P style=Heading2] Reliable automation design
[P style=] Commerce events enter the outbox, then a worker evaluates the current customer, order and consent state. Save a deduplication key such as orderId plus eventType. Use a global cap such as two promotional messages per week initially, with separate limits for each automation. Treat all timings here as starting hypotheses to test.
[P style=Heading2] Sender reputation
[P style=] Use a transactional email provider with verified sending domains. [P style=] Measure clicks, purchases, unsubscribes and complaints. Open rates are unreliable because privacy features can prefetch images. Prefer campaign revenue and conversion with attribution limits. Store no bought email lists, and do not send deals to visitors who never provided an address and marketing permission.

[P style=ListBullet] Accurate product images, weights, dimensions, opening stock, tax configuration and legally appropriate customer policies.
[P style=ListBullet] Production backups, alert recipients, customer support contact, email domain authentication and successful live pilot refunds.
[P style=Heading2] Definition of a complete launch
[P style=] The owner can add and publish stock, a guest can pay and track delivery, a customer can manage their account, staff can fulfill and refund, and the business can reconcile money. The system remains usable when optional tracking is rejected. Release gates measure these outcomes rather than counting pages or components.
[P style=] 

[P style=Heading1] 26 Acceptance tests and release checklist
[P style=] Prioritize tests that protect money, access, stock and customer communications. Use unit tests for pricing and state rules, integration tests against PostgreSQL for transactions, provider sandbox tests, and Playwright for critical browser journeys.
[TABLE]
| ID | Scenario | Pass condition |
| A01 | Account and session | Register, verify, login and logout work; revoked session cannot access private data. |
| A02 | Guest checkout and claim | Guest places order without registration; access requires verification; account claim links only verified orders. |
| A03 | Admin authorization | Catalog staff cannot refund or change roles; direct API calls are rejected and logged. |
| A04 | Product publication | Product, images, category, title, description, price, stock and JSON-LD become consistent without a deployment. |
| A05 | Last unit race | Two concurrent orders for one unit cannot create two valid reservations or negative stock. |
| A06 | Payment authenticity | Forged, wrong-amount and wrong-currency events cannot mark paid; valid duplicates have one effect. |
| A07 | Retry and reconciliation | A lost response or webhook resolves to the original attempt, without a duplicate charge or abandoned captured order. |
| A08 | Refund and shipping | Partial refund cannot exceed captured balance; partial shipping cannot exceed purchased quantity; return disposition controls restock. |
| A09 | Privacy and email | Reject optional cookies: no optional tags fire. Withdraw email permission: queued offers stop; operational notices still work. |
| A10 | Search and accessibility | Useful HTML and canonical links exist; structured data validates; checkout supports keyboard and readable error states. |
| A11 | Failure recovery | Worker restart, duplicate event and provider outage preserve order correctness and expose an actionable retry queue. |
| A12 | Operations | Backup restore succeeds; logs redact secrets; alerting works; reconciliation balances the live pilot orders. |
[/TABLE]
[P style=Small] 
[P style=Heading2] Suggested performance gates
[P style=] Load-test realistic catalog filters and checkout concurrency. Start with a documented target such as 50 concurrent checkout attempts with no integrity errors; increase to the forecast launch load. Set internal API latency and error budgets from staging measurements, excluding the external provider delay rather than hiding it from customer timings.
[P style=] Measure Core Web Vitals on mobile, not only a desktop Lighthouse score. Keep a rollback procedure ready, use backward-compatible migrations, and prevent fulfillment of unverified payments during the pilot. [14]
[P style=] 

[P style=Heading1] 27 Deployment operations and cost planning
[P style=Heading2] Deployment topology
[P style=] Host the Next.js application on a suitable managed platform or Node runtime, and deploy NestJS and workers as long-running processes with health checks. Use managed PostgreSQL, Redis, object storage and a CDN. Ensure a shared catalog-cache strategy if Next.js runs on multiple instances. Keep application regions close to the database.
[TABLE]
| Operational area | Required process |
| CI and release | Lint, type check, test, dependency review, build, migration dry run, staging acceptance, then controlled production deployment. |
| Database | Connection pooling, least-privilege users, slow-query monitoring, daily backups and point-in-time recovery where available. |
| Events and jobs | Retry policy, dead-letter queue, idempotent consumers and alerts for lag. Reconcile unfinished work from PostgreSQL, not Redis alone. |
| Payments | Daily compare orders, attempts, refunds, provider statements and settlement bank records. Investigate mismatches and aged processing states. |
| Monitoring | Track checkout failures, webhook errors, stock conflicts, publication lag, email bounces, courier sync age and unusual admin actions. |
| Incident response | Named owner, support contact, disable affected gateway if necessary, retain evidence, communicate order impact and document recovery. |
| Recovery targets | Initial business targets: RPO 15 minutes and RTO 4 hours if funded and technically supported; prove with a restore exercise. |
| Catalog growth | Use pagination and selective indexes; measure search relevance and query latency before adding a dedicated search cluster. |
[/TABLE]
[P style=Small] 
[P style=Heading2] Budget categories
[P style=] Request separate quotes for engineering, design and QA; cloud application hosting; database and Redis; storage and image delivery; transactional and promotional email; observability; payment processing and FX; courier and returns; security review; and ongoing maintenance. Costs depend on order volume, geography, catalog and provider contracts, so do not treat a hosting quote as the whole operating budget.
[P style=Heading2] Initial operating rhythm
[P style=] Daily: payment reconciliation, dispatch exceptions, stock alerts and failed jobs. Weekly: query and sales performance, email complaints, returns and admin audit review. Monthly: dependency maintenance, restore drill or documented recovery check, access review, customer feedback and experiment results.
[P style=] Launch with the smallest dependable configuration and reserve maintenance time. Advanced recommendations, loyalty points and a native app should follow evidence of demand, not delay a working store.
